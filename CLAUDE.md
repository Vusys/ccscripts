# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ComputerCraft/CC:Tweaked turtle automation scripts in Lua, distributed via GitHub. There is no build system or test framework in the traditional sense (these are Minecraft-API-dependent scripts that only really run on a turtle/CraftOS-PC), but there is a real install/update mechanism: `install.lua` (a one-shot `wget` bootstrap) and `pkg.lua` (a small package manager), driven by `manifest.json`. See README.md for the user-facing install/usage instructions.

## CC:Tweaked API reference

Run `scripts/fetch-cc-tweaked-reference.sh` to pull a local reference into `reference/cc-tweaked/` (gitignored, ~3MB, takes a couple seconds — safe to re-run any time). It's a trimmed clone of [cc-tweaked/CC-Tweaked](https://github.com/cc-tweaked/CC-Tweaked) (`mc-1.21.x` by default): the hand-written docs (`doc/`), the actual bundled Lua ROM source (`bios.lua`, `rom/apis/*.lua`, `rom/programs/*`, `rom/modules/main/cc/*`), and every Java source file implementing a Lua-facing method (`@LuaFunction`). See `reference/cc-tweaked/README.md` (written by the script) for the full breakdown.

**Use this instead of guessing or web-searching CC:Tweaked/Lua-on-CC:Tweaked behavior.** It's caught real mistakes in this repo before: `flex.getHex()` originally used `math.log(x, 2)`, which doesn't exist in the Lua 5.1 CC:Tweaked actually runs (that's a Lua 5.2+ feature) — the ROM source in this reference would have shown that immediately. `turtle.inspect()`'s exact return shape (`{name, state}`, no `metadata` field) came from `doc/reference/block_details.md`, not assumption. When the reference isn't there yet (or the answer isn't obviously in it), run the fetch script first — don't fall back to training-data recall for anything CC:Tweaked-API-specific, since that's exactly the kind of thing that goes stale or was subtly wrong to begin with.

## Repo layout vs. on-device layout

The repo is organized into folders (`lib/`, `programs/`, `config/`), but **every install is flat** — `manifest.json` maps each entry's repo-relative `path` to a flat on-device `install_as` filename (e.g. `lib/dig.lua` → `dig.lua`). This matters because CC:Tweaked's `require()` resolves relative to the *requiring program's own directory*; keeping the on-device install flat means `require("dig")`/`require("flex")` just work with zero `package.path` setup, regardless of how the repo itself is organized. **When adding a new file: put it wherever makes sense in the repo tree, but give it a flat `install_as` in `manifest.json` and never introduce a subdirectory on the on-device side.**

## Module Architecture

```
programs/quarry.lua, treefarm.lua, corridor.lua, ...  →  lib/job.lua  →  lib/dig.lua  →  lib/flex.lua
programs/tunnel.lua, fasttunnel.lua, dig-cli.lua  ───────────────────────────↗
(programs)                              (job scaffold)  (motion API)   (utility API)
```

Modules are loaded with `require()`, not the deprecated `os.loadAPI()` — `local dig = require("dig")`, `local flex = require("flex")`, `local job = require("job")`. Each returns a table; there is no global-namespace state. `lib/job.lua` is the one exception to "returns a table": `job.new(opts)` is a *factory* (a program calls it once to get a fresh instance of closures) rather than a singleton, since — unlike `dig`/`flex`, where a program only ever drives one turtle — a program could in principle run more than one job in sequence, each needing its own throttle timer and milestone counters.

- **lib/flex.lua** — Utility API. Inventory consolidation (`condense`), wireless broadcasting (`send` for a human-readable string, `sendData` for a structured table — see Wireless protocol below), block/item detection (`getBlock`/`isBlock`/`isItem`/`isFluid`), colored terminal output (`printColors`, inline `#X` hex color codes, degrades to plain text on non-color terminals, `escapeMarkup` for safely embedding untrusted text like a computer label), config I/O for `flex_options.cfg`.
- **lib/dig.lua** — Motion, mining, and crash-recovery API. Coordinate tracking (X=right, Y=up, Z=forward, R=rotation in degrees), getter/setter pattern for all state (e.g. `dig.getx()`/`dig.setx()` — internal state is closed over as upvalues, never accessed directly), navigation (`goto`, `gotox`/`gotoy`/`gotoz`/`gotor`), retry-and-dig-through movement with a 20-second stuck timeout (applies uniformly to `fwd`/`up`/`down`), placement (fluid-aware retry, same timeout), fuel management, save/resume state, and vein-following mining (`mineVein(dir)` — recursively follows every 6-connected block matching the `[ores]` `dig_options.cfg` list from the given direction, then returns to the exact position/facing it was called from; capped at `MAX_VEIN_BLOCKS` as a defensive bound). Depends on flex.lua.
- **lib/job.lua** — Shared "supervised job" scaffold for any long-running program (fuel-low round trip, inventory-full round trip, redstone pause/resume gate via `rs.getInput("top")`, and the throttled wireless status heartbeat — see Wireless protocol below). `job.new({kind, fuelEstimate, dump, total, extra, workingState})` returns an instance exposing `broadcast`/`heartbeat`/`checkFuel`/`checkInv`/`checkHalt`/`checkProgress`/`gotoBase`/`returnFromBase`. Pulled out of `quarry.lua` once it became clear every job-shaped program would otherwise reimplement (and re-debug) the same housekeeping; `quarry.lua` is both the first extraction source and the first consumer. Depends on dig.lua and flex.lua.
- **programs/dig-cli.lua** — `save`/`load`/`clear`/`edit`/`colors` subcommands for a person to run interactively. This used to be baked into `dig.lua` itself as a top-level CLI dispatch; it's a separate program now so `dig.lua` can be a pure `require()`-able module with no side effects beyond returning its API table.
- **programs/quarry.lua** — `quarry <length> [width] [depth] [skip <N>] [dump] [nolava] [nether] [vein]`. Zigzag/boustrophedon strip-mining, layer by layer. Sweep direction is derived purely from layer/column position parity (not any persisted flag), which is what makes a mid-layer reboot resumable without extra bookkeeping. Pause via redstone signal on `rs.getInput("top")`, automatic inventory dumps, and wireless progress reporting — both `flex.send()` human-readable messages and `lib/job.lua`'s structured status heartbeat for `monitor.lua` — all delegated to a `job.new({kind = "quarry", ...})` instance; quarry only keeps the housekeeping that's actually quarry-specific (lava sealing at the excavation's edges, a y-depth progress milestone, and — opt-in via `vein` — chasing any ore vein visible through the excavated volume's boundary via `dig.mineVein()`) local to itself.
- **programs/treefarm.lua** — `treefarm <rows> <cols> [passes <N>] [dump]`. Tends a grid of tree plots: cruises above canopy height between plots, descends straight through each plot's column (dig.lua's existing dig-through movement fells whatever trunk is in the way as a side effect of just moving down — no separate "chop" step needed), replants bare ground, leaves an already-growing sapling alone. Runs forever by default (`passes` bounds it); reboot-resumable the same zero-extra-bookkeeping way quarry is, since revisiting an already-tended plot is a no-op.
- **programs/farm.lua** — `farm <rows> <cols> [passes <N>] [dump]`. Same shape as treefarm.lua but for single-block-tall crops (wheat/carrots/potatoes/beetroot/nether wart): walks the grid directly (no cruise altitude needed), harvests+replants via `inspectDown`'s real block `state.age` (the block's actual Minecraft blockstate property, confirmed against `doc/reference/block_details.md` rather than assumed) against a per-crop max-age table, leaves an immature crop alone.
- **programs/build.lua** — `build <schematic.json> [dump]`. Constructs a structure from a JSON schematic (`{layers: [[[cellName, ...], ...], ...]}`, X-outer/Z-inner per layer, bottom-to-top) already on the turtle's filesystem, selecting each cell's named block from the inventory by substring match. Builds each layer by flying one cell above it and using `placeDown()` — never standing where a block needs to go. Schematic cells use `""` for "leave empty", deliberately not JSON `null`: `textutils.unserialiseJSON` turns `null` into a real Lua `nil` by default, which would put a hole in the middle of a row array. Missing materials are skipped (not blocked on, unlike `dig.refuel()`) and reported once at the end. Layer index and control height (`dig.gety()`) coincide 1:1, so a reboot resumes at the right layer with no extra bookkeeping, same resumability philosophy as quarry/treefarm/farm.
- **programs/bridge.lua** — `bridge <length> [dump]`. Walks forward, checking `flex.isFluid("down")` (which covers plain air too, not just liquids) after each step and `placeDown()`-ing from a reserved slot (`dig.setBlockSlot()`, same mechanism quarry uses for lava-sealing) whenever there's nothing solid underneath. Stays at the far end when done — `job.lua`'s `checkFuel()` round trip still works mid-bridge regardless, since it walks back over the floor already placed.
- **programs/well.lua** — `well [maxDepth] [dump] [return]`. Digs straight down via `dig.down()` until either `maxDepth` is reached or `dig.isStuck()` (bedrock) — for a well, hitting bedrock is the expected way to finish, not a failure condition.
- **programs/corridor.lua** — `corridor <length> [return]`. Digs a straight, 1-wide passage: at each position it clears the block above and below in place via `dig.dig("up")`/`dig.dig("down")` (the same idiom as `fasttunnel.lua`'s `clearColumn()`, but with no vertical movement — the turtle never leaves floor level) and then advances through the block in front via `dig.fwd()`. Distinct from `tunnel.lua` with `width=1`/`height=2`, which would actually climb into the space above and dig from there instead of reaching into it, and wouldn't touch the block below at all. Deliberately skips `job.lua`'s `checkInv()` *and* `checkFuel()` — no dump option, no output chest, no low-fuel round trip to a base chest; it just mines forward and stops at its destination, unlike every other `job.lua`-based program here. Fuel awareness still comes for free from `dig.lua` itself — `fwd()`/`dig()` call `refuel(1)` on every move, which blocks waiting for more fuel in the onboard fuel slot rather than going anywhere to fetch it.
- **programs/courier.lua** — `courier <length> [trips <N>] [dump] [idle]`. Shuttles items between a pickup chest behind the start (`turtle.suck()`, after turning around) and a dropoff chest ahead of the far end (reuses `dig.dropNotFuel()` wholesale, forward-facing exactly as it expects). The pickup chest's placement isn't arbitrary — it's exactly where `job.lua`'s own `checkFuel()`/`checkInv()` round trips already return to and face (`gotoBase()` ends at `r=180`), so it does double duty as the base chest for those. `idle` blocks on a wireless `{kind="courier_request"}` (`flex.sendData`) before each trip instead of shuttling continuously.
- **programs/relay.lua** — rebroadcasts everything heard on `modem_channel` back out verbatim on the same channel, extending effective wireless range (wireless modems are range-limited — 64 blocks at low altitude, up to 384 at world height, see `ModemPeripheral`'s doc comment in the reference). Deliberately single-hop: a modem never receives its own transmission back (confirmed against `ModemPeripheral.java`'s `packet.sender() == this` check), so one relay is always safe, but two relays whose ranges overlap would ping-pong a retransmission back and forth forever — documented as a hard constraint (don't deploy overlapping relays), not solved in code. No `dig.lua` dependency, same as `monitor.lua`.
- **programs/monitor.lua** — companion fleet dashboard: listens for `flex.sendData()` broadcasts (`kind == "job_status"`) from *any* `lib/job.lua`-based program and renders a live per-turtle status table (turtle name, job kind, state, position, fuel, dug/total progress, and a job-specific `extra` detail line), grouped by job kind with a per-kind count summary at the top (`quarry:2 treefarm:1 ...`), plus a scrolling log of any plain-text `flex.send()` messages on the same channel. Renders to a `monitor` peripheral if one's attached (`term.redirect`), else the terminal. No dependency on `dig.lua` — it never moves anything, just listens.
- **pkg.lua** / **install.lua** — the install/update mechanism, both at repo root (root keeps the `wget run` URL short, and `install.lua` in particular needs to be trivially discoverable). `install.lua` is a deliberately minimal one-shot bootstrap (run via `wget run`) that does **not** resolve dependencies transitively — it only downloads whatever the manifest flags `first_run: true` — so every entry a `first_run: true` program directly `require()`s must itself be flagged `first_run: true` too (this is why `job` is `first_run: true`: `quarry` requires it directly). `pkg.lua` does everything after that (list/install/update/remove/refresh, with real transitive dependency resolution via `resolveDeps`), reading `manifest.json` from the repo over `http.get` + `textutils.unserialiseJSON`.

## Wireless protocol

Two distinct message shapes travel over the same modem channel (`flex_options.cfg`'s `modem_channel`, default 6464 for everyone):

- `flex.send(message, textColor)` transmits a **string** with inline `#X` color markup — for a person watching another computer's terminal. Always echoed locally and logged to `log.txt`.
- `flex.sendData(table)` transmits a **raw Lua table** — CC:Tweaked's modem delivers it back out as a table on the receiving end, no serialization step needed. Not echoed or logged (it's meant to be called often, as a heartbeat, not as a one-off event). Give it a `kind` field so a listener consuming several message shapes can tell them apart without erroring on ones it doesn't recognize. Every `lib/job.lua`-based program sends the same common shape — `{kind = "job_status", job, id, label, state, x, y, z, r, fuel, fuelLimit, dug, total, extra}` — where `job` is the program's own name (`"quarry"`, `"treefarm"`, ...), `state` is one of `paused`/`refueling`/`dumping`/`done`/`stuck`/or the program's own `workingState` (quarry uses `"mining"`), and `extra` is an optional table of whatever detail is specific to that job kind (quarry's `{length, width, depth, skip}`, for instance) — `monitor.lua` renders it generically as a `key=value` line, so a new job kind shows up on the dashboard with zero changes to `monitor.lua` itself.

Anything embedding free-form/untrusted text (a computer label, in particular) into a `#X`-formatted string must run it through `flex.escapeMarkup()` first — a literal `#` immediately followed by a hex digit is otherwise misread as a color-switch escape rather than printed literally. This bit a first draft of `monitor.lua` for the deterministic case of `"turtle #" .. id` (an id's first digit always collides); the fix is now centralized in `flex.escapeMarkup` rather than duplicated per caller.

## Configuration Files

- **dig_options.cfg** (on-device, flat) — Block classification lists: `[outputblocks]` (chests), `[blacklist]` (protected blocks — only enforced when `dig.doBlacklist(true)` is set), `[buildingblocks]` (scaffolding), `[dumplist]` (discard), `[fluids]`, `[ores]` (vein-following target list for `dig.mineVein()` — defaults to the single substring `ore`, which matches every vanilla ore name, plus `ancient_debris` separately since its name doesn't contain "ore"). Seeded from `config/dig_options.default.cfg` on first install; pkg never overwrites an existing one.
- **flex_options.cfg** (on-device, flat) — `modem_channel` (default 6464) and `name_color`. Seeded from `config/flex_options.default.cfg` the same way.
- Both live files are gitignored — only the `*.default.cfg` shipped defaults are tracked. Runtime-generated files (`dig_save.cfg`, `dig_fuel.cfg`, `log.txt`, `startup.lua`, `pkg_installed.json`, `pkg_manifest_cache.json`, `pkg_config.cfg`) are gitignored too — they're produced on-device, never authored by hand.

## Key Patterns

- **State persistence**: `dig.lua` saves a 17-value array to `dig_save.cfg` (16 original fields, plus an additive 17th "extra" string field via `getExtra()`/`setExtra()` that `dig.lua` itself ignores — it exists so a calling program can persist one small piece of its own state across a reboot instead of overloading an unrelated field) and writes a `startup.lua` to auto-resume after reboot. The 17-value order is a de facto public contract (`goto()` accepts this array directly) — any change must be additive, never reordering/removing existing fields.
- **API loading**: `require("dig")` / `require("flex")`, not `os.loadAPI()`. Modules are pure — no top-level CLI argument handling or other side effects beyond returning their API table.
- **Getter/setter pattern**: all `dig.lua` state is closed over as `local` upvalues, exposed only through getter/setter function pairs (e.g. `dig.getx()`/`dig.setx()`).
- **Stuck detection**: movement functions (`fwd`/`up`/`down`) retry-and-dig for 20 real-world seconds before reporting failure, uniformly. Unbreakable blocks are logged to an in-memory bedrock list and reported via `flex.send`. The same 20-second bound applies to plain `dig()`/`digUp()`/`digDown()` (reaching into a space without moving there) via the shared `digUntilClear()` helper — without it, a falling block (sand/gravel) or anything else that keeps refilling the space (a hopper/dispenser) would make `digFn()` keep returning `true` forever, since "the block keeps coming back" never naturally exits a `while digFn() do ... end` loop. This shipped as a real bug: `corridor.lua`'s `clearColumn()` (`dig.dig("up")`/`dig.dig("down")`) spun forever under a sand column before the fix — `fasttunnel.lua`'s identical `clearColumn()` idiom had the same latent exposure, just never hit it in testing.
- **Fuel awareness**: `dig.refuel()` blocks until enough fuel is available (intentionally — it has nowhere else to go); calling programs like `quarry.lua` are responsible for noticing low fuel and returning to base themselves (`dig.lua` has no "return to surface" logic of its own).
- **Lua 5.1 target**: CC:Tweaked runs Lua 5.1 semantics. No `math.log(x, base)` (2-arg form is 5.2+), no bitwise operators, no `goto`/labels as statements. Verify anything version-sensitive against a real `lua5.1` interpreter, not just a syntax check — `luac5.1 -p` catches parse errors but not stdlib differences like the missing 2-arg `math.log`.
- **`turtle` isn't always present**: `flex.lua` is required by non-turtle programs too (`programs/monitor.lua` runs on a plain computer with just a wireless modem). Never reference `turtle.*` in a table literal or other expression that evaluates at module-load time (`local INSPECT = { fwd = turtle.inspect, ... }` crashes `require("flex")` outright on a computer with no turtle — this shipped once, see the fix in `flex.lua`'s `getBlock`/`INSPECT`, and the equivalent in `dig.lua`'s `DIG`/`PLACE`). Build such tables lazily, guarded by `if turtle then ... end`, so only actually *calling* a turtle-only function fails on a non-turtle computer — not merely requiring the module. The `no_turtle_test.lua` pattern in the scratch test harness (`turtle = nil` before requiring) is exactly for catching this class of bug.
- **Testing without a turtle**: there's no CC:Tweaked emulator in this environment, so changes are verified with a mocked-API smoke test (stub `turtle`/`fs`/`term`/`http`/etc. globals, `require()` the real files, exercise them, including a simulated mid-job reboot for `dig.lua`/`quarry.lua`'s save/resume path). Write throwaway test harnesses in a scratch directory, not into the repo.
- **Program names collide with stock CC:Tweaked turtle programs**: `/rom/programs/turtle/` ships its own `craft`/`dance`/`equip`/`excavate`/`go`/`refuel`/`tunnel`/`turn`/`unequip` (see `reference/cc-tweaked/.../rom/programs/turtle/`). CraftOS's shell path is `.:/rom/programs:/rom/programs/turtle` — current directory first — so an installed same-named program in this repo normally wins. But if it *isn't* actually installed (fresh turtle, `pkg install` skipped/failed), the shell silently falls back to the stock version instead of erroring, which is confusing: our `tunnel.lua` takes `<width> <height> <length>`, the stock one takes only `<length>`, so running the real 3-arg command against a not-yet-installed turtle just prints the stock program's one-arg usage line — it looks like a broken CLI rather than a missing install. Before naming a new program, check it isn't already a stock name; when debugging a program that "only takes one argument" it didn't get, check `pkg list` for whether it's actually installed before assuming the arg-parsing code is at fault.
